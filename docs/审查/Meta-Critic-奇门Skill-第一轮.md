## 1. CRITIQUE ANALYSIS 批评分析

### 效能分析
当前稿能引导模型做三件事：查 `knowledge/`、不编造、跨卡时看 `_Ontology.md` 与四条硬规矩。对「查概念／按书给步骤」场景基本够用。但对 Day3 需求（可安装、触发准、适合公开履历）偏弱：frontmatter `description` 只有定位，没有用户会说的原话，宿主靠 description 匹配时命中不稳；正文缺边界与输出模板，模型容易在边缘题上「感觉对就答」。

### 精确性评估
期望：触发准、不编造、跨卡先读 Ontology、硬规矩可执行、可上 GitHub。  
实际差距：
- 触发：description 写「回答奇门遁甲相关问题」，偏术语简介，缺「空亡是什么」「帮我起一局」等原话 → 触发精度不够。
- 不编造：有「资料里没有」句，但未列已知缺口（晴雨用神符号、8 案例推理过程、九遁三祚五假），模型可能在缺口区硬猜或空泛拒答且说不清原因。
- 跨卡：步骤 1 写「先读 knowledge/」，步骤 4 才写跨卡读 Ontology → **顺序冲突**；「跨卡」仅举三类问法，未覆盖「起一局十步」「有没有对应格」等也必须先关系层。
- 硬规矩：四条写得硬，可执行；与底座口径一致，是本稿最大资产。
- 履历：缺边界、缺输出规范、缺已知限制，公开仓 README 再好，Skill 本体仍像「半成品操作备忘」。

### 边缘情况识别
1. 用户问非奇门（八字／六爻）→ 无拒答边界。  
2. 一词多卡或文件名含异名括号（如空亡／旬空）→ 「按文件名定位」过粗。  
3. 同时要概念定义 + 起局顺序 → 先卡还是先 Ontology 未写死。  
4. 问「值使临戊有没有格」→ 应走 §2.6/§6.1，若只搜卡名可能就近借名。  
5. 起盘算术错（定局／旬首／值使）→ 无「必须提示用户核三处」。  
6. Ontology 与卡冲突 → 有规矩 4，好；但未要求**同时披露冲突点**。  
7. 用户只要闲聊口吻解释 → 仍应注出处，未强调。

### 优势要素
- 四条硬规矩（推断≠原文、两说并存、无格不借名、冲突以卡为准）清晰可执行。  
- Ontology 问题类型→章节对照表，可检索。  
- 「不许自己编」+ 固定拒答句，方向正确。  
- 知识库规模与查法（先列目录、不必全读）务实。  
- 与精简 Ontology 底座职责切分清楚（关系层不重复卡内容）。

### 弱点暴露
- 结构：工作方式四条扁平列表，把「何时读什么」揉在一起，决策树缺失。  
- 语义：`description` 不符合 Skill规范 v1.3「定位＋范围＋触发原话」。  
- 缺开场自报、边界三句、收口、输出格式。  
- 「先读 knowledge/」过宽，易导致跨卡题跳过 Ontology。  
- 未把安装说明里的「已知缺口」沉到 Skill 本体（装说明有、Skill 无 → Agent 运行时看不到）。

## 2. REVISION STRATEGY 修改策略

### 校准理论
- description 当**触发关键词表**，不是简介。  
- 一条指令只对应一个可观察动作（先读谁、再读谁、输出什么）。  
- 负面约束要可检验（「不许编」→ 固定句 + 已知缺口清单）。

### 结构重构
建议顺序：frontmatter → 开场自报 → 边界 → **读库决策树** → 知识库查法 → Ontology 路由表 + 硬规矩 → 输出格式 → 收口。

### 语义增强
- 「跨卡」扩成：关系／顺序／用神／有无格／同指／应期／起局断局流程 → 一律先 `_Ontology.md`。  
- 单概念定义／单卡步骤 → 先目录匹配再读卡。  
- 推断挂接、两说并存：输出里强制带标签。

### 鲁棒性提升
- 非本域拒答；已知三缺口点名；起盘附核验三处；卡名歧义时列候选让用户确认或按 Ontology §5。

### 输出规范化
固定四块：结论／依据（卡名）／关系依据（Ontology 节）／不确定或推断标注。禁止无出处断语。
